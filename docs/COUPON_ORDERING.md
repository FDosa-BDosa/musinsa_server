# 쿠폰 발급 성능/순서 가이드 (Redis Lua 단일 원자 실행)

## 핵심 요약
- **분산락은 제거**하고 Redis Lua로 `중복 체크 → 재고 차감 → TTL 설정`을 **한 번의 원자 명령**으로 처리합니다.
- 1,000명이 동시에 와도 Redis가 네트워크 도착 순서대로 처리하므로 **정확하게 100명에게만 발급**되며, 별도 락이 없어 **지연이 짧고 TPS가 높습니다.**
- 순서 자체가 중요한 경우에는 **락 대신 순차 큐(Kafka 단일 파티션, Redis Stream 단일 shard, 단일 컨슈머 리스트)** 로 직렬화하세요.

## 왜 분산락을 빼야 할까?
- 락을 잡고 Lua를 실행하면 **락 경합 + Lua 실행** 두 번의 대기 비용이 생겨 성능이 떨어집니다.
- Lua 스크립트는 Redis에서 단일 명령으로 실행되므로 **추가 락 없이도 임계구간이 보호**됩니다.
- 발급 정확도(재고 초과/중복 방지)와 빠른 응답이 목적이라면 **락을 추가할 실익이 없습니다.**

## 권장 아키텍처
1. **API 레이어**
   - Lua 스크립트로 중복 여부와 재고를 검증하고 감소시킵니다.
   - 성공 결과만 **비동기 큐**에 적재해 DB 반영을 분리합니다.
2. **큐 소비자(워커)**
   - 큐에서 순차로 꺼내 DB에 저장하고, `(coupon_id, user_id)` 유니크 제약으로 중복을 한 번 더 차단합니다.
3. **모니터링/백프레셔**
   - Redis CPU/latency, 큐 적체량, DB 저장 실패(중복/제약 위반) 카운터를 관찰해 워커 스케일을 조절합니다.

## 구현 포인트 (현재 코드 기준)
- `CouponIssueLuaScript`는 **락 없이** 중복 체크, 재고 차감, TTL 설정을 한 번에 수행합니다.
- `CouponIssuanceService.issueCoupon`은 Lua 결과만으로 즉시 응답하고, 성공 시 `CouponIssueQueueProducer`에 적재합니다.
- `CouponIssueQueueWorker`가 큐를 읽어 트랜잭션으로 DB에 반영하며, 중복 인서트 예외는 로깅 후 무시합니다.
- 순서를 엄밀히 맞춰야 하면 큐를 **단일 컨슈머**로 운용하거나 Kafka/Redis Stream 단일 파티션을 사용합니다.

## 성능 테스트 팁
- Redis `INFO commandstats`와 `latency doctor`로 Lua 실행 시간을 확인합니다.
- 큐 적체량(길이)과 워커 처리 속도(TPS)를 대조하여 병목을 찾습니다.
- API는 Redis 응답만으로 반환하므로, 워커 처리 지연이 길어져도 **발급 정확도**는 유지됩니다.
